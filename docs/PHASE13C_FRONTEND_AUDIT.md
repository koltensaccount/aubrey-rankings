# Phase 13C — Frontend and product alignment audit

**Baseline:** production health and `origin/main` both reported `2c9ed0ad920d015fd6a596c5935c182114653d1f` on 19 October 2026. Audit branch: `audit/phase13c-frontend`.

**Evidence and limits.** This is a code and product audit, not a claim that every control was exercised. Source links below point to the implementation inspected; classifications describe recommendations, not implemented changes. Guest production pages `/`, `/discover`, and `/feed` were loaded in headless Chromium at 320, 375, 390, 430, 768, and 1440 px; `/login` and guest TMDB search were checked over HTTP. At 320 px the document reported 10 px horizontal overflow on all three pages after loading; the overflowing element was not isolated. At other measured widths it reported no document overflow. Mobile public navigation was present below 768 px. No authenticated browser session was available: authenticated, owner, non-owner, touch, keyboard, modal, and light/dark observations below are static-code findings or risks, not visually verified interaction results. The production journal privacy smoke test was also limited by the absence of private journal rows. Existing tests provide useful regression coverage but are not a substitute for those journeys.

## Executive assessment

The primary routes and much of the underlying model exist: global and collection-scoped ratings, weighted and tier rubrics, first-class reviews, visibility, following, and a library. Feed defaults to Following for authenticated users, and mobile guest navigation exists. The product remains fragmented: the library is a long set of sections rather than three views; creation leads only to rankings; Discover has no ranking search or actual curated community landing; several ranking/review editors and calls to action overlap. Some controls promise actions they do not perform. Privacy-sensitive review-to-rating association and the displayed community mean require particular attention before amplifying discovery.

## Information architecture and visual direction

- Use one Create control in the global shell, opening two clear choices: **Rate or Review** (title/episode search, then unified journal) and **Create Ranking** (existing type and scoring workflow). Put account/profile, Settings and Sign out together; retain notification access and mobile bottom navigation.
- Library has three peer views: **Rankings**, **Journal**, **Saved**. Keep filters/search close to content, use pagination or incremental loading with stable ordering, and avoid a featured cover until a ranking is intentionally pinned. Preserve collection-specific versus global scores, legacy reviews and resume paths.
- Discover starts with title/people/public-ranking search and curated real public content; reviews are reached through title and creator. Feed remains chronological community activity, default Following for signed-in users, with Community as a second choice. Do not make Discovery a second feed or populate it with invented activity.
- Replace “canon,” “critical dispatch,” and “personal workspace” with ranking, review, journal and library when those are the actual objects. Avoid implying a title is already in a ranking merely because a search query was prefilled.
- Retain theme variables, current artwork treatments, typography and TMDB attribution. Use shared buttons/dialog primitives and fewer nested borders and pills; recommendations for aesthetics require authenticated visual review before any redesign.

## Responsive and visual verification

The guest automated viewport checks are described above; no screenshots or authenticated interactions were used to infer owner behavior. The shared header has a fixed 80 px height and multiple authenticated actions; settings uses a horizontally scrollable tab row, collection filters wrap, and several custom modals bypass the shared dialog primitive. These are **inspection targets**, not confirmed visual failures. Check 320/375/390/430 px, tablet and desktop in light/dark with keyboard, zoom, screen reader, touch, long titles, error/loading states, safe-area insets, and long forms. Pay particular attention to report trigger vs bottom navigation, bottom content padding, dialog header/footer visibility, artwork containment and floating slider values. Use semantic focus and existing `--radius-*`, `--shadow-*`, surface and accent tokens.

## Phase 13D — recommended sequence

1. Resolve and test public review score consent, visibility defaults, community-average suppression/eligibility and scale semantics before exposing additional discovery. Preserve current data and add owner/non-owner/anonymous tests.
2. Repair confirmed false or broken affordances: guest search handling, Compare feed mapping, People deep link, inert import/export presentation, login return path and journal draft resume.
3. Implement the agreed universal Create and account menu, preserving mobile/guest navigation. Unify Library into Rankings / Journal / Saved, with explicit pinning, stable pagination, deduplication and search/filter semantics.
4. Make Discover search titles, people and eligible public rankings with truthful empty/error states; retain Followed-first Feed and simplify its controls. Define the public search/rate-limit boundary and avoid synthetic content.
5. Exercise authenticated desktop and mobile journeys, permissions, keyboard and both themes; use existing component primitives and focused regression tests. Do not change scoring formulas, migrations, importer behavior or private legacy content as a byproduct.

## Phase 13E / 13F follow-up

**13E — reuse:** define eligibility for public ranking and rubric reuse, attribution and ownership; implement an explicitly created new object with selected public structural fields only. Never clone another person's private notes, ratings, drafts, engagement or hidden data. Address ownership, visibility, snapshot vs link, rubric changes and permission/revocation in both UI and server validation. This is a future plan, not existing functionality.

**13F — visual polish:** after IA and permission fixes, inspect real populated and empty states at all target widths and themes. Refine density, artwork, gradients, type hierarchy, buttons and focus using the existing tokens; do not build a new design system or add decorative controls.

## Decisions needed

1. Should publishing a journal review include its personal rating only after a separate explicit opt-in, or is a clearly labeled combined publish confirmation sufficient? How should already published linked reviews retain their behavior?
2. For the provisional 10-person Aubrey average, define eligible public signals, one vote per user/title, rating method and scale normalization, exclusions (imports, duplicates, blocks, tiers), rounding, and whether a user may opt in/out. Never silently include private ratings. Confirm TMDB vote-count/label and availability rules.
3. Can guests search TMDB via a bounded public proxy, or should Discover clearly require sign-in for title search? Which curated ranking sources and pagination rules should be used?
4. Should review default settings apply to legacy independent reviews while journal entries remain private by default, and should changing the spoiler default affect only future writing?
5. Pin policy: one or multiple pinned rankings, ordering, and how pinning appears on profile versus Library. Resolve search/filter ordering and behavior when a saved ranking becomes private.
6. For community reuse, decide eligible visibility, attribution, copy-versus-linked rubric semantics and whether reuse is allowed after an original becomes private. These decisions are for 13E, not implied implementation approval.
